Execution Plan

Detailed Analysis Summary

Change Impact Assessment

  • User-facing changes: Yes. 고객용 태블릿 웹UI와 관리자용 웹UI를 새로 만듭니다.
  • Structural changes: Yes. 처음부터 시스템 구조를 정합니다.
    • React+Vite 프론트엔드
    • FastAPI 백엔드 (REST API, SSE)
    • SQLite
  • Data model changes: Yes. 엔티티 9종을 새로 정의합니다.
    • Store, AdminUser, LoginAttempt, Table, TableSession, Category, Menu
    • Order(보관 표시 archived_at 포함), OrderItem
  • API changes: Yes. 새로 만드는 API는 다음과 같습니다.
    • REST API: 인증, 메뉴, 주문, 테이블
    • SSE 스트림: 관리자용 1종, 테이블용 1종
  • NFR impact: Yes, 범위는 제한적입니다.
    • 실시간 반영 2초 이내
    • JWT/bcrypt 인증과 로그인 시도 제한
    • 매장 간, 테이블 간 데이터 분리
    • Security/PBT/Resiliency extension은 모두 비활성입니다.

Risk Assessment

  • Risk Level: Medium-Low. 로컬에서 돌리는 MVP이고 운영 영향이 없습니다. 기술적으로 불확실한 부분은 SSE 연동과 상태 동기화입니다.
  • Rollback Complexity: Easy. 신규 프로젝트이고 운영 데이터가 없습니다.
  • Testing Complexity: Moderate.
    • 메뉴 항목 상태 전이, 세션 라이프사이클, SSE 이벤트 전달을 검증해야 합니다.
    • 단위 테스트와 API 통합 테스트를 합니다.

Phases to Execute

🔵 INCEPTION PHASE

  • Workspace Detection (COMPLETED)
  • Reverse Engineering (SKIPPED — greenfield)
  • Requirements Analysis (COMPLETED)
  • User Stories (COMPLETED)
  • Execution Plan (IN PROGRESS)
  • Application Design - EXECUTE (standard depth)
    • Rationale: 모든 컴포넌트가 새로 생기므로 아래 항목을 코드 작성 전에 정해야 합니다.
      • 백엔드 서비스 계층: 인증, 주문, 항목 상태, 테이블 세션, SSE 이벤트 브로커
      • 프론트엔드 구조: 고객용과 관리자용을 앱 1개로 만들지 2개로 나눌지
      • SSE 채널 설계: 매장 채널, 테이블 채널
  • Units Generation - EXECUTE (minimal depth)
    • Rationale: 백엔드와 프론트엔드는 기술 스택과 빌드가 다릅니다. 그래서 작업 단위를 나누고 구현 순서와 API 계약 의존성을 정해야 합니다.
    • 예상 단위는 2~3개입니다.
      • backend
      • 프론트엔드 1개 또는 2개 (customer-web, admin-web)
    • 최종 개수는 Application Design 결과에 따라 확정합니다.

🟢 CONSTRUCTION PHASE

  • Functional Design - EXECUTE (backend unit만)
    • Rationale: 핵심 비즈니스 규칙을 코드 전에 정확히 정의해야 합니다.
      • 메뉴 항목 상태 머신, 주문 상태 자동 결정
      • 예상 시간 계산과 수정
      • 테이블 세션 시작/종료 트랜잭션, 주문 보관 표시
      • 주문 번호 채번
      • 로그인 잠금
      • DB 스키마
    • 프론트엔드 unit은 상태 관리 로직이 단순해서 생략합니다. 대상은 장바구니, SSE 구독, 카운트다운입니다. 이 부분은 스토리의 인수 조건과 Code Generation 계획에서 다룹니다.
  • NFR Requirements - SKIP
    • Rationale:
      • 기술 스택은 이미 확정되었습니다. (FastAPI, React+Vite, SQLite, SSE)
      • NFR 목표도 requirements.md 5절에 수치로 정의되어 있습니다.
      • Security/Resiliency extension이 비활성이라 추가 평가할 항목이 없습니다.
  • NFR Design - SKIP
    • Rationale: NFR Requirements를 생략하므로 함께 생략합니다. 아래 항목은 Application Design과 Functional Design에서 다룹니다.
      • SSE 재연결
      • 트랜잭션 처리
      • 인증 미들웨어
  • Infrastructure Design - SKIP
    • Rationale: 클라우드 리소스가 없는 로컬 실행 MVP입니다. 실행 환경은 Code Generation에서 함께 만듭니다.
      • Docker Compose 파일
      • 로컬 실행 스크립트
  • Code Generation - EXECUTE (ALWAYS, unit별)
    • Rationale: 각 unit의 코드, seed 데이터, 테스트를 생성합니다.
  • Build and Test - EXECUTE (ALWAYS)
    • Rationale: 아래 항목을 작성하고 실제로 실행해서 검증합니다.
      • 빌드 및 실행 방법 (Docker Compose, 로컬)
      • 백엔드 pytest
      • 프론트엔드 Vitest
      • 고객↔관리자 연동 시나리오 테스트

🟡 OPERATIONS PHASE

  • Operations - PLACEHOLDER
    • Rationale: 향후 배포/모니터링 워크플로용

Estimated Timeline

  • 남은 단계: 5종 (Application Design, Units Generation, Functional Design, Code Generation, Build and Test)
  • 승인 게이트: unit을 3개로 나누면 약 7~9회입니다.
  • 예상 진행: 설계 문서 3종을 만든 뒤, backend → frontend 순서로 코드를 생성하고 통합 테스트를 합니다.

Success Criteria

  • Primary Goal: 로컬에서 실행되는 테이블오더 MVP. 37개 스토리의 인수 조건을 충족해야 합니다.
  • Key Deliverables:
    • FastAPI 백엔드 (REST + SSE, SQLite, seed 데이터)
    • React+Vite 고객용/관리자용 웹UI
    • Docker Compose 및 로컬 실행 방법
    • pytest / Vitest 테스트
  • Quality Gates:
    • 백엔드/프론트엔드 빌드 성공
    • 단위 및 API 테스트 통과
    • 다음 흐름이 실제로 동작하는지 수동 시나리오로 확인
      1. 주문
      2. 대시보드 표시
      3. 준비 시작
      4. 고객 카운트다운
      5. 완료 배너
      6. 이용 완료 후 태블릿 초기화
