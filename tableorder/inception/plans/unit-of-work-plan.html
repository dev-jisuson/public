Unit of Work Plan

목적

Application Design의 컴포넌트를 개발 단위(Unit of Work)로 나누고 다음 세 가지를 정합니다.

  • 각 단위가 맡는 스토리
  • 단위 간 의존성
  • 구현 순서

분해 근거 (분석 결과)

  • 배포 구조: 독립 배포 서비스가 아닙니다. 아래 두 덩어리를 Docker Compose 하나로 함께 실행합니다.
    • 백엔드: FastAPI 단일 프로세스
    • 프론트엔드: React+Vite 앱 1개
  • 기술 경계: 백엔드와 프론트엔드는 다음이 모두 다릅니다. 그래서 둘을 자연스러운 분해 경계로 봅니다.
구분 백엔드 프론트엔드
언어 Python TypeScript
빌드 pip/uv npm
테스트 pytest Vitest
  • 계약 경계: 두 단위는 아래 두 가지로만 통신합니다 (component-methods.md 4~5절).
    • REST 엔드포인트 20개
    • SSE 이벤트 4종
  • 질문 생략 카테고리
    • Team Alignment: 개발 주체가 1명(사용자 + AI)이라 소유권을 나눌 필요가 없습니다.
    • Technical Considerations(단위별 확장성 차이): 로컬 MVP라 단위별로 다른 확장 요구가 없습니다.
    • Business Domain: 매장 1개 범위의 단일 도메인입니다. 세부 경계는 백엔드 서비스 계층에서 이미 나눴습니다.

실행 체크리스트 (승인 후 생성)

  • 1. unit-of-work.md — 단위 정의, 책임, 포함 컴포넌트, 코드 구성(디렉터리 구조) 전략
  • 2. unit-of-work-dependency.md — 단위 의존 매트릭스, 통합 계약, 구현 순서
  • 3. unit-of-work-story-map.md — 37개 스토리를 단위에 매핑
  • 4. 단위 경계와 의존성 검증 (순환 없음, 계약 일치)
  • 5. 모든 스토리가 하나 이상의 단위에 배정되었는지 확인

Question 1

개발 단위를 몇 개로 나눌까요?

A) 2개 — backend(API, SSE, DB, seed)와 frontend(고객용 + 관리자용 화면). 단위마다 설계 → 코드 → 승인을 한 번씩 거치므로 승인 횟수가 가장 적음 (추천)

B) 3개 — backend, frontend-table(고객 화면), frontend-admin(관리자 화면). 같은 프론트엔드 앱 안의 모듈을 순서대로 구현. 단위 크기가 작아서 검토하기 쉽지만 승인 횟수가 늘어남

C) 1개 — 전체를 한 단위로 한 번에 구현. 승인은 가장 적지만 코드 생성 결과물이 매우 커서 검토하기 어려움
