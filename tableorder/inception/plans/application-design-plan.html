Application Design Plan

목적

requirements.md와 stories.md(37개 스토리)를 바탕으로 아래 세 가지를 정의합니다.

  • 컴포넌트 경계와 책임
  • 메서드 시그니처
  • 서비스 간 오케스트레이션과 통신 방식

상세 비즈니스 규칙(상태 전이 규칙, 스키마 상세)은 이후 Functional Design에서 다룹니다.

설계 범위 (분석 결과)

  • 백엔드 기능 영역
    • 인증: 관리자, 태블릿, 로그인 잠금
    • 메뉴 조회
    • 주문 생성/조회/삭제
    • 메뉴 항목 상태와 예상 시간
    • 테이블/세션 관리: 이용 완료, 과거 이력
    • 실시간 이벤트(SSE)
  • 프론트엔드 기능 영역
    • 고객 화면: 설정, 메뉴, 장바구니, 주문, 주문 내역, 완료 배너
    • 관리자 화면: 로그인, 대시보드, 주문 상세, 테이블 관리, 과거 내역
  • SSE 채널 2종
    • 매장 채널: 관리자가 구독
    • 테이블 채널: 태블릿이 구독

실행 체크리스트 (승인 후 생성)

  • 1. components.md — 컴포넌트 정의 및 책임 (백엔드 / 프론트엔드)
  • 2. component-methods.md — 메서드 시그니처, 입출력 타입
    • 2.1 백엔드 서비스/리포지토리 메서드
    • 2.2 REST API 엔드포인트 목록
    • 2.3 SSE 이벤트 타입 및 페이로드 개요
  • 3. services.md — 서비스 정의 및 오케스트레이션 (주문 생성, 상태 변경, 이용 완료 흐름)
  • 4. component-dependency.md — 의존 관계 매트릭스, 통신 패턴, 데이터 흐름도
  • 5. application-design.md — 위 문서 통합본
  • 6. 설계 완결성 점검 (37개 스토리가 컴포넌트에 모두 매핑되는지)

Question 2

백엔드 코드 구조는 어떻게 나눌까요?

A) 계층형 — router(API) → service(비즈니스 로직) → repository(DB 접근). 비즈니스 로직을 테스트하기 쉬움 (추천)

B) 단순형 — router에서 ORM을 직접 호출. 코드량은 적지만 로직이 API 코드와 섞임

Answer A (채팅: "추천안으로 가자.")

Question 3

DB 접근 라이브러리는 무엇을 쓸까요?

A) SQLAlchemy 2.0 — 가장 널리 쓰이고 트랜잭션 제어가 명확함. 이용 완료 처리의 원자성에 유리 (추천)

B) SQLModel — SQLAlchemy + Pydantic 통합. 코드는 짧지만 고급 기능은 결국 SQLAlchemy 문법 필요

C) ORM 없이 표준 라이브러리 sqlite3 + 직접 SQL

X) Other (please describe after [Answer]: tag below)

Answer A (채팅: "추천안으로 가자.")

Question 4

SSE 이벤트를 연결된 화면들에 전달하는 방식은 어떻게 할까요?

A) 서버 프로세스 내부의 메모리 이벤트 브로커 (asyncio 큐). 서버는 프로세스 1개로 실행. 추가 인프라가 없어 MVP에 적합하고, 이후 Redis로 바꿀 수 있게 인터페이스로 분리 (추천)

B) Redis Pub/Sub — 서버를 여러 프로세스로 늘릴 수 있지만 Redis 컨테이너가 추가로 필요

X) Other (please describe after [Answer]: tag below)

Answer A (채팅: "추천안으로 가자.")

Question 5

SSE 이벤트에 어떤 데이터를 담을까요?

A) 변경된 데이터를 이벤트에 직접 포함 — 예: order_item.updated 이벤트에 항목 상태와 예상 완료 시각을 담음. 화면이 바로 갱신되고, 재연결 시에만 전체를 다시 조회 (추천)

B) 알림만 보내고 화면이 API로 다시 조회 — 예: table.changed 이벤트를 받으면 주문 목록 재요청. 구현은 단순하지만 요청 수가 늘어남

X) Other (please describe after [Answer]: tag below)

Answer A (채팅: "추천안으로 가자.")

Question 6

SSE 연결의 인증은 어떻게 할까요? (참고: 브라우저 기본 EventSource는 Authorization 헤더를 보낼 수 없습니다)

A) 토큰을 URL 쿼리 파라미터로 전달 — 예: /api/sse/table?token=.... 추가 라이브러리가 필요 없음. 대신 토큰이 서버 접근 로그에 남을 수 있는데, 로컬 MVP에서는 수용 가능 (추천)

B) fetch 기반 SSE 라이브러리(@microsoft/fetch-event-source)로 Authorization 헤더 전달 — 토큰이 URL에 노출되지 않지만 프론트엔드 의존성이 1개 늘어남

X) Other (please describe after [Answer]: tag below)

Answer A (채팅: "추천안으로 가자.")

Question 7

프론트엔드 상태 관리(장바구니, 로그인 정보, 실시간 주문 상태)는 어떻게 할까요?

A) Zustand — 작고 단순함. persist 기능으로 장바구니/로그인 정보의 localStorage 저장이 쉬움 (추천)

B) React 기본 기능만 사용 (Context + useReducer) — 의존성은 없지만 localStorage 저장 코드를 직접 작성해야 함

C) Redux Toolkit — 기능은 많지만 이 규모에는 무거움

X) Other (please describe after [Answer]: tag below)
