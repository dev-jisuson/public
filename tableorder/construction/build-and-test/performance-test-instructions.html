Performance Test Instructions

요구사항 (requirements.md NFR)

  • 신규 주문, 상태 변경, 이용 완료 이벤트가 SSE로 2초 이내 반영
  • 규모: 매장 1개(식당 1곳) MVP, SQLite 단일 파일, uvicorn 워커 1개

실행

cd backend
.venv/bin/python -m tests_integration.perf_sse                                        # 기본: 관리자 구독 50, 주문 200건, 동시 10
.venv/bin/python -m tests_integration.perf_sse --subscribers 200 --orders 500 --workers 20   # 가혹한 조건
  • 임시 DB와 실제 uvicorn 프로세스를 띄워서 측정하고 끝나면 정리합니다. 지연은 "주문 POST 직전 ~ 각 관리자 스트림이 이벤트를 받은 시각"입니다 (같은 PC, 로컬 루프백).

결과 (2026-10-14, Apple Silicon 노트북)

조건 처리량 POST p50 / p95 / max 주문→SSE 수신 p50 / p95 / max 누락·오류 판정
관리자 구독 50 + 태블릿 6, 주문 200건, 동시 10 259 건/초 9 / 101 / 658 ms 8 / 100 / 658 ms (10,000건 측정) 0 / 0 PASS (2초 대비 3배 여유)
관리자 구독 200 + 태블릿 6, 주문 500건, 동시 20 160 건/초 34 / 530 / 2,219 ms 28 / 513 / 2,218 ms (100,000건 측정) 0 / 0 FAIL (최대값만 2초 초과)
  • GET /api/admin/dashboard 평균 4~5ms (주문 500건 후에도)
  • 서버 종료: 열린 SSE 스트림이 있어도 2.2초

해석

  • 현실적인 규모(테이블 수십 개, 주문이 초당 몇 건 이하)에서는 지연이 100ms 수준으로 요구사항을 크게 만족합니다.
  • 두 번째 조건은 한 매장의 실제 사용량을 훨씬 넘는 동시 주문 20개 연타 + 관리자 화면 200개입니다. 최대 지연이 늘어난 원인은 SSE 전달이 아니라 주문 쓰기 자체의 대기입니다(POST max도 2.2초). SQLite는 쓰기를 한 번에 하나씩 처리하고(BEGIN IMMEDIATE), 동시 쓰기가 줄을 섭니다. 이벤트는 커밋 뒤에 바로 발행되므로 POST가 끝난 시점과 SSE 수신 시점의 차이는 작습니다.
  • 조치하지 않았습니다 (MVP 범위). 이 한계가 문제가 되는 규모라면 다음 순서로 검토하세요: ① PostgreSQL 전환 ② 이벤트 브로커를 Redis 등으로 분리해 워커 확장 ③ 주문 번호 채번 분리.

알려진 한계

  • 브로커가 프로세스 메모리에 있어 워커 1개만 지원합니다 (다중 워커/다중 서버에서는 이벤트가 다른 프로세스로 전달되지 않음).
  • 구독자 큐(256개)가 넘치는 느린 클라이언트는 연결이 끊기고, 클라이언트가 재연결 후 전체 상태를 다시 조회합니다.
  • 브라우저/네트워크 지연, 실제 태블릿 성능, 장시간(수 시간) 연결 유지는 측정하지 않았습니다.
