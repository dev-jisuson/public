Business Logic Model — backend

규칙 ID(BR-*)는 business-rules.md를 가리킵니다.

1. 주문 생성 (US-C10~C12, US-I01)

입력: 태블릿 토큰, 항목 목록 [{menu_id, quantity}]

  1. 토큰에서 store_id, table_id를 얻습니다. (BR-ORDER-1)
  2. 입력을 검증합니다. (BR-ORDER-3, 4)
    • 줄 수 1~20, 수량 1~20, menu_id 중복 없음
  3. 해당 매장의 메뉴를 조회해 모든 menu_id가 있는지 확인합니다. 하나라도 없으면 전체 거부. (BR-ORDER-5)
  4. 트랜잭션 시작
    1. 테이블의 활성 세션을 찾고, 없으면 새로 만듭니다. (BR-ORDER-9)
    2. 지금 시각을 KST 날짜로 바꿔 business_date를 정합니다.
    3. (store_id, business_date) 카운터를 1 올려 order_no를 만듭니다. (BR-NO-1~4)
    4. 각 줄에 메뉴명/단가 스냅샷을 담아 OrderItem을 만들고, 총액을 계산합니다. (BR-ORDER-2, 6)
    5. Order(상태 PENDING)와 OrderItem(모두 PENDING)을 저장합니다. (BR-ORDER-7)
  5. 커밋. 실패하면 모두 취소하고 이벤트를 보내지 않습니다. (BR-ORDER-8)
  6. order.created를 매장 채널과 해당 테이블 채널에 발행합니다.
  7. OrderDTO를 응답합니다.

2. 메뉴 항목 상태 변경 (US-A08~A11, US-I02)

2.1 준비 시작 / 예상 시간 수정 / 완료 (항목 1개)

  1. 항목을 찾고 관리자 매장 범위인지 확인합니다. 아니면 NOT_FOUND. (BR-ITEM-8)
  2. 주문이 보관됐으면 ORDER_ARCHIVED. (BR-ITEM-7)
  3. 전이 표에서 현재 상태와 요청 동작이 허용되는지 확인합니다. 아니면 INVALID_STATE_TRANSITION.
  4. 시간 입력이 필요한 동작이면 1~120 정수인지 확인합니다. 아니면 VALIDATION_ERROR. (BR-ITEM-1)
  5. 항목 필드를 갱신합니다. (BR-ITEM-2, 3, 4)
  6. 주문의 모든 항목 상태로 주문 상태를 다시 계산해 저장합니다. (BR-STATUS-1~4)
  7. 커밋 후 order_item.updated를 발행합니다.

2.2 전체 준비 시작 (주문 1개)

  1. 주문을 찾고 범위/보관 여부를 확인합니다.
  2. PENDING 항목을 모읍니다. 없으면 INVALID_STATE_TRANSITION. (BR-ITEM-5)
  3. 시간 입력을 검증합니다.
  4. 모은 항목 전체에 같은 now로 준비 시작을 적용합니다.
  5. 주문 상태를 다시 계산하고 커밋한 뒤 order_item.updated를 한 번(항목 여러 개 포함) 발행합니다.

주문 상태 계산 (순수 함수)

derive_order_status(statuses):
    if all(s == PENDING):   return PENDING
    if all(s == COMPLETED): return COMPLETED
    return PREPARING

예: 파스타 x3, 콜라 x1 주문

시점 파스타 콜라 주문 상태
주문 직후 PENDING PENDING PENDING
콜라 완료(준비 시작 후) PENDING COMPLETED PREPARING
파스타 준비 시작(12분) PREPARING COMPLETED PREPARING
파스타 완료 COMPLETED COMPLETED COMPLETED

파스타 x3 중 1개만 나가는 중간 상태는 없습니다. 줄 전체가 완료돼야 COMPLETED입니다.

3. 주문 삭제 (US-A13, US-I04)

  1. 주문을 찾고 범위를 확인합니다. 없으면 NOT_FOUND, 보관됐으면 ORDER_ARCHIVED. (BR-DELETE-1, 2)
  2. 주문과 항목을 삭제합니다.
  3. 같은 세션의 남은 현재 주문 총액과 미완료 항목 수를 다시 계산합니다. (BR-DELETE-4)
  4. 커밋 후 order.deleted를 발행합니다. 세션은 유지합니다. (BR-DELETE-5)

4. 이용 완료 (US-A14, US-I03)

  1. 테이블을 찾고 범위를 확인합니다.
  2. 활성 세션이 없으면 아무것도 바꾸지 않고 {session_id: null, archived_order_count: 0}을 성공으로 응답합니다. 이벤트는 보내지 않습니다. (BR-SESSION-6)
  3. 트랜잭션: 세션의 archived_at이 없는 주문 전부에 archived_at = now, 세션에 ended_at = now. (BR-SESSION-3)
  4. 커밋. 실패하면 전부 취소하고 이벤트도 보내지 않습니다. (BR-SESSION-8)
  5. table.session_completed를 매장 채널과 해당 테이블 채널에 발행합니다.

5. 과거 내역 조회 (US-A15)

  1. 테이블을 찾고 범위를 확인합니다.
  2. 그 테이블의 archived_at이 있는 주문을 created_at 내림차순(동률이면 ID 내림차순)으로 가져옵니다.
  3. date가 있으면 주문 시각의 KST 날짜가 같은 주문만 남깁니다. (BR-VIEW-6)
  4. cursor/limit로 잘라서 응답합니다. 각 주문에 session_id, archived_at이 들어갑니다.

6. 대시보드와 재동기화 (US-A04~A07, US-I03, US-I05)

대시보드 (관리자)

매장의 각 테이블마다:

  1. 활성 세션을 찾습니다. 없으면 session_id: null, 총액 0, 주문 0건, 미완료 0, 미리보기 없음.
  2. 있으면 활성 세션의 현재 주문에서 total_amount 합, 주문 수, COMPLETED가 아닌 항목 수, 최신 3개 주문을 계산합니다. (BR-VIEW-3, 4, BR-STATUS-5)

태블릿 상태 (GET /api/table/state)

  • 자기 테이블의 활성 세션 ID와 현재 주문 전체, 서버 시각을 돌려줍니다. 활성 세션이 없으면 session_id: null, orders: [].
  • 태블릿은 응답의 session_id가 자기가 저장한 값과 다르면 장바구니와 주문 내역을 비웁니다(프론트엔드 규칙).

7. 로그인과 잠금 (US-C01, US-A01, US-A03)

login(kind, store_code, identifier, password):
    attempt = find(kind, store_code, identifier)
    if attempt.locked_until > now:
        raise ACCOUNT_LOCKED(locked_until)                  # BR-LOCK-3
    if attempt.locked_until <= now (잠금이 끝남):
        attempt.fail_count = 0; attempt.locked_until = null # BR-LOCK-4

    subject = find_account(...)                              # 없으면 None
    if subject is None or not verify(password, subject.hash):
        attempt.fail_count += 1
        if attempt.fail_count >= 5:
            attempt.locked_until = now + 15min               # BR-LOCK-2
        save(attempt)
        raise INVALID_CREDENTIALS                            # BR-AUTH-2

    attempt.fail_count = 0; attempt.locked_until = null      # BR-LOCK-5
    return issue_token(subject, 16h)
  • 5번째 실패 응답은 INVALID_CREDENTIALS이고, 6번째 시도부터 ACCOUNT_LOCKED입니다.
  • 존재하지 않는 계정도 같은 경로로 기록됩니다. (BR-LOCK-6)

8. SSE 이벤트

채널 규칙 (BR-SCOPE-3)

채널 구독자 키
매장 채널 관리자 store:{store_id}
테이블 채널 해당 테이블 태블릿 table:{table_id}

모든 이벤트는 커밋 성공 후에만, 해당 매장 채널과 영향받는 테이블의 채널에 발행합니다. 다른 테이블 채널에는 보내지 않습니다. (US-I02 AC3)

이벤트 봉투

id:    프로세스 안에서 증가하는 정수 (재연결 때 재전송에는 쓰지 않음)
event: 이벤트 타입
data:  {"sent_at": "서버 시각", ...아래 페이로드}

15초마다 : ping 주석 줄을 보냅니다. 재연결 때 놓친 이벤트를 다시 보내지 않고, 클라이언트가 상태 API를 다시 호출해 맞춥니다. sent_at은 클라이언트가 시계 차이를 보정해서 카운트다운에 사용합니다.

페이로드

이벤트 페이로드
order.created order(OrderDTO), table_id, table_number, table_total, unfinished_item_count
order.deleted order_id, table_id, table_total, unfinished_item_count
order_item.updated items[](OrderItemDTO, 바뀐 항목만), order_id, order_status, table_id, unfinished_item_count
table.session_completed table_id, session_id, completed_at, archived_order_count
  • order_item.updated에서 items[]에 COMPLETED로 바뀐 항목이 있으면 태블릿이 완료 토스트를 띄웁니다. 토스트에 쓸 메뉴명은 menu_name으로 들어 있습니다.
  • 대시보드는 이벤트를 받으면 table_total, unfinished_item_count를 그대로 카드에 반영합니다.

10. 동시성 정리

  • 쓰기는 모두 트랜잭션 1개로 처리하고, 데이터베이스가 쓰기를 직렬화합니다.
  • 두 관리자가 같은 항목을 동시에 바꾸면 나중 요청은 바뀐 상태를 보고 전이 표에 따라 거부(409)됩니다.
  • 활성 세션이 테이블당 1개라는 제약은 데이터베이스 제약으로도 보장합니다.
  • 같은 주문 요청을 연속으로 두 번 보내는 중복 제출은 백엔드가 막지 않습니다. 프론트엔드가 전송 중 버튼을 비활성화합니다.
