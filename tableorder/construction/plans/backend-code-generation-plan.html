Code Generation Plan — backend

이 문서가 backend Code Generation의 유일한 기준입니다. 승인 후 순서대로 실행하고, 끝낸 단계는 즉시 [x]로 바꿉니다.

범위 변경 (2026-10-14T14:20 사용자 지시: "인증 관련된건 다 빼도 돼. MVP니까")

  • 제외: 로그인/로그아웃, JWT, 비밀번호(bcrypt), 로그인 잠금, AdminUser·LoginAttempt, 테이블 비밀번호 등록/변경, SSE 토큰 검증, 토큰 종류 검사
  • 대체: 요청이 X-Store-Code(없으면 기본 매장 demo), 태블릿은 X-Table-Number 헤더로 매장/테이블을 식별. SSE는 헤더를 못 쓰므로 쿼리 store_code, table_number.
  • 유지: 매장·테이블 범위 격리(타 매장 데이터 404), 주문/상태/세션/SSE/seed 전부
  • 영향 스토리: US-C01~C03, US-A01~A03은 구현 제외, US-A12는 "테이블 등록(번호)"만 구현, US-I06은 헤더로 식별한 범위 안에서 격리
  • 주의: 모든 엔드포인트가 인증 없이 열려 있음 (로컬 MVP 전용, 공개 배포 금지)

단위 정보

  • 단위: backend (Unit 1)
  • 코드 위치: tableorder/backend/ (aidlc-docs/ 안에는 코드를 두지 않음)
  • 문서 위치: aidlc-docs/construction/backend/code/ (마크다운 요약만)
  • 프로젝트 유형: Greenfield, 다중 단위({unit-name}/ 패턴)
  • 기준 설계: functional-design/{domain-entities,business-rules,business-logic-model}.md, application-design/*

담당 스토리 (unit-of-work-story-map.md 기준 backend 담당)

US-C04, C10~C16, US-A04~A06, A08~A15, US-I01~I06 (인증 스토리 C01~C03, A01~A03은 MVP에서 제외, frontend 단독 스토리 C05~C09, A07 제외)

의존성과 계약

  • 다른 단위에 의존하지 않습니다. frontend가 이 단위의 REST/SSE 계약(component-methods.md 4~5절)에 의존합니다.
  • 소유 엔티티: Store, Table, TableSession, Category, Menu, Order, OrderItem, DailyOrderCounter

기술 선택 (확정)

  • Python 3.12 이상, FastAPI, SQLAlchemy, SQLite, pytest, httpx
  • 의존성 버전은 설치 가능한 실제 버전을 확인해서 pyproject.toml에 정확한 버전으로 고정합니다.
  • 마이그레이션 도구(Alembic)는 쓰지 않습니다. MVP이므로 시작 시 테이블이 없으면 생성하고 seed를 적재합니다. (Database Migration Scripts 단계는 이 이유로 생략)
  • 구현 결정(설계 문서에 없는 세부)
    • SQLite 파일 경로는 DATABASE_URL(기본 backend/data/tableorder.db), 연결 시 외래키 제약을 켭니다.
    • 서비스는 시계(now)를 주입받을 수 있게 해서 테스트에서 시간을 고정합니다.
    • 활성 세션 1개 제약은 SQLite 부분 유니크 인덱스로 보장합니다.

실행 단계

A. 구조와 기반

  • Step 1. 프로젝트 구조 설정
    • backend/pyproject.toml, backend/.env.example, 루트 .gitignore(DB 파일, 가상환경, node_modules 등)
    • 디렉터리와 __init__.py 생성: app/{api,core,services,repositories,models,schemas,seed}, tests/
  • Step 2. Core 모듈
    • core/config.py, core/database.py, core/errors.py(도메인 예외 + 오류 응답 변환), core/deps.py(get_db, 매장/테이블 컨텍스트 해석: 헤더/쿼리), core/clock.py

B. 데이터 계층

  • Step 3. ORM 모델 — models/ : 8개 엔티티(Store, DiningTable, TableSession, Category, Menu, DailyOrderCounter, Order, OrderItem), 제약(유일 키, 활성 세션 부분 유니크 인덱스), 관계
  • Step 4. Pydantic 스키마 — schemas/ : 요청/응답 DTO, SSE 페이로드, 오류 응답
  • Step 5. 리포지토리 — repositories/ : 리포지토리. 모든 조회가 store_id 범위 안에서만 동작
  • Step 6. 리포지토리 단위 테스트 — 범위 격리(다른 매장 데이터 안 보임), 주문 번호 카운터, 활성 세션 제약, 보관 주문 조회

C. 비즈니스 로직

  • Step 7. 이벤트 인프라 — services/events.py : EventBroker 인터페이스, InMemoryEventBroker, EventPublisher(매장 채널 + 해당 테이블 채널)
  • Step 8. (제외됨) 인증 서비스 — 사용자 지시로 범위에서 뺌
  • Step 9. 도메인 서비스
    • MenuService, TableService, TableSessionService(이용 완료 = 보관 표시)
    • OrderService(주문 생성/삭제/현재 세션 조회, 주문 번호), OrderItemService(상태 전이, derive_order_status)
    • DashboardService, OrderHistoryService, TableStateService
    • 커밋 성공 후에만 이벤트 발행
  • Step 10. 비즈니스 로직 단위 테스트
    • 상태 전이 표 전체(허용/거부), 주문 상태 자동 결정, 예상 시간 계산/수정, 전체 준비 시작
    • 주문 생성 검증(수량/줄 수/중복/없는 메뉴/타 매장 메뉴), 금액·스냅샷, 번호 채번(자정 초기화, 삭제 후 미재사용)
    • 이용 완료(보관 표시, 총액 0, 활성 세션 없음일 때 no-op, 미완료 항목 있어도 허용), 주문 삭제 후 세션 유지
    • 실패 시 롤백 + 이벤트 미발행

D. API 계층

  • Step 11. 라우터 — api/ : table, admin_dashboard, admin_order, admin_table, sse (로그인 엔드포인트 제외, 정적 파일)
  • Step 12. 앱 조립 — app/main.py : 라우터 등록, 오류 처리기, /static 마운트, 시작 시 테이블 생성 + seed 적재, 헬스체크 GET /api/health
  • Step 13. API 테스트
    • 메뉴 → 주문 → 대시보드 → 상태 변경 → 이용 완료의 전체 흐름
    • 매장/테이블 격리(US-I06): 타 매장 리소스 404, 타 테이블 주문 미노출
    • SSE: 주문 생성 시 관리자·해당 태블릿만 수신, 다른 테이블 태블릿은 미수신, 이용 완료 이벤트, 재동기화용 상태 API

E. Seed와 정적 자원

  • Step 14. Seed와 이미지 — seed/seed.py(멱등, 매장·테이블 1~6·메뉴), static/images/ 메뉴별 SVG 12개 + placeholder.svg, seed 테스트

F. 문서와 배포

  • Step 15. 문서 — backend/README.md(실행 방법, API 문서 주소 /docs), aidlc-docs/construction/backend/code/code-summary.md
  • Step 16. 배포 산출물 — backend/Dockerfile(단일 워커), 루트 docker-compose.yml의 backend 서비스 + DB 볼륨 (frontend 서비스는 frontend 단위에서 추가)
  • Step 17. 동작 확인 — 로컬 가상환경에서 pytest 실행, 서버를 실제로 띄워 GET /api/health, 메뉴 조회, SSE 연결 확인. 결과를 요약에 기록
