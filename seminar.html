세미나 진행 순서

AI-DLC로 테이블오더 MVP를 만든 과정을 팀원에게 소개하는 순서입니다. 권장 시간은 약 45분(진행 37분 + 정리·Q&A 8분)이며, 산출물이 실제로 생긴 순서를 그대로 따라갑니다.

# 주제 시간 보여줄 페이지
0 오프닝 영상 2분 세미나 영상
1 AI-DLC 한눈에 보기 5분 AI-DLC 소개
2 과제 소개 3분 사례 개요, 원본 요구사항
3 Inception ① 요구사항 질문 7분 질문 1차, 2차, 3차, 요구사항 정리
4 Inception ② 스토리와 실행 계획 5분 유저 스토리, 실행 계획
5 Inception ③ 설계와 유닛 4분 애플리케이션 설계, 유닛–스토리 매핑
6 Construction ① 기능 설계와 코드 생성 6분 도메인 엔티티, 코드 생성 계획, 코드 요약
7 Construction ② 빌드와 테스트 3분 빌드·테스트 요약, 성능 테스트
8 기록: audit와 state 2분 audit.md, aidlc-state.md
9 정리와 Q&A 8분 사례 개요 — 건너뛴 단계

0. 오프닝 영상 (2분)

  • 2분 요약 영상으로 전체 그림(단계, 질문 51개, 화면, 테스트 결과)을 먼저 보여 준다.

1. AI-DLC 한눈에 보기 (5분)

보여줄 페이지: AI-DLC 소개

  • Inception → Construction → Operations 세 단계. 각 단계 안의 스테이지는 "항상 실행"과 "조건부"로 나뉘고, AI가 과제를 보고 어느 조건부 스테이지를 돌릴지 제안한다.
  • 스테이지마다 사람이 리뷰하고 승인해야 다음으로 넘어간다.
  • v1.0.1은 마크다운 규칙 32개가 전부다. Claude Code에서는 core-workflow.md를 CLAUDE.md로 두고 상세 규칙을 .aidlc-rule-details/에 두면 된다.
  • 산출물은 aidlc-docs/에, 코드는 워크스페이스 루트에 쌓인다.

2. 과제 소개 (3분)

보여줄 페이지: 사례 개요, 원본 요구사항, 예외사항

  • 입력은 마크다운 2개(요구사항 정의서, 예외사항)뿐이다. 첫 지시는 "requirements/ 디렉토리안에 md파일 2개를 읽고 ai-dlc 워크플로를 시작해줘." 한 줄.
  • 만든 것: 손님 태블릿 주문 화면(/table) + 매장 관리자 실시간 주문 화면(/admin). 유닛은 backend(FastAPI + SQLite + SSE), frontend(React + Vite) 2개.
  • 걸린 시간: 시작부터 Build and Test 승인까지 약 3시간(중간 기록 공백 약 1시간 10분 포함).

3. Inception ① 요구사항 질문 (7분)

보여줄 페이지: 질문 1차 → 2차 → 3차 → 요구사항 정리

  • AI가 질문 파일을 만들고, 사람은 [Answer]: 뒤에 선택지를 적는다. 질문과 답이 파일로 남는다.
  • 1차 12문항: 기술 스택, 저장소, 실시간 통신 등 Q1–Q9와 확장 규칙(Security, PBT, Resiliency) 적용 여부 3개.
  • 2차 8문항: 1차 답변에 덧붙인 "예상 시간 표시 / 서빙 직전 완료 처리" 아이디어의 모호한 점을 AI가 다시 물었다.
  • 3차 7문항: "니가 다시 문서 다 읽어봐"라는 요청에 AI가 원본 문서끼리 어긋난 부분(메뉴 관리 범위, "16시간 세션"과 "테이블 세션" 등)을 찾아 재질문했다.
  • 사람이 개입한 장면: 메뉴 관리를 "넣자"고 했다가 1분도 안 돼 "MVP니까 디폴트 메뉴 기반으로" 번복했고, 나머지는 "니 추천대로"로 정리했다.
  • 결과물 requirements.md: 기술 결정 표(질문 번호가 근거로 붙음)와 AI가 세운 가정이 명시돼 있다.

4. Inception ② 스토리와 실행 계획 (5분)

보여줄 페이지: 페르소나, 유저 스토리, 실행 계획

  • 스토리 37개(Epic 10개). 모든 스토리의 인수 조건이 Given/When/Then 형식이다.
  • Workflow Planning에서 AI가 이후 스테이지의 실행·생략을 근거와 함께 제안하고, 사람이 승인했다.
  • 생략한 스테이지: Reverse Engineering(그린필드), NFR Requirements·NFR Design(스택과 목표가 이미 정해짐), Infrastructure Design(로컬 MVP).

5. Inception ③ 설계와 유닛 (4분)

보여줄 페이지: 애플리케이션 설계, 유닛 정의, 유닛–스토리 매핑

  • 컴포넌트·서비스·메서드·의존성을 한 문서로 묶은 통합본. 주문 → SSE → 관리자 화면으로 이어지는 시퀀스 다이어그램을 보여 준다.
  • 유닛은 backend, frontend 2개. 매핑 표에서 스토리 37개가 모두 유닛에 배정된 것을 확인한다.

6. Construction ① 기능 설계와 코드 생성 (6분)

보여줄 페이지: 도메인 엔티티, 비즈니스 규칙, 백엔드 코드 생성 계획, 백엔드 코드 요약

  • 기능 설계는 backend 유닛만 진행했다(ER 다이어그램, 비즈니스 규칙).
  • 진행 중에 "최대한 construction 단계를 빠르게 끝내야해. 대부분 추천안으로 적용해서 진행해줘."라고 지시했다. 이후 AI는 추천안을 기본으로 적용했지만 승인 단계는 유지했다.
  • 코드 생성은 계획(backend 17단계, frontend 14단계)을 먼저 승인받고 체크박스를 채우며 진행한다.
  • 범위 변경: 코드 생성 도중 "인증 관련된건 다 빼도 돼. MVP니까"라는 지시로 로그인·JWT·잠금을 제거하고 매장 코드·테이블 번호 헤더로 식별하게 바꿨다. 앞 단계 설계 문서는 그대로 남아 있어, 어긋나는 부분을 코드 요약에 기록했다.
  • 백엔드 테스트 중 버그 3개를 AI가 찾아 고쳤다.

7. Construction ② 빌드와 테스트 (3분)

보여줄 페이지: 빌드·테스트 요약, E2E 테스트, 성능 테스트

  • 테스트: backend pytest 73, frontend Vitest 115(이후 UI 개선 후 131), 실제 서버 연동 9, 실제 Chrome E2E 7 모두 통과.
  • 주문 → 관리자 화면 반영 42–85ms.
  • 성능: 관리자 구독 50·주문 200건은 PASS(최대 658ms). 구독 200·주문 500건·동시 20은 최대 2,218ms로 2초 기준 FAIL(SQLite 쓰기 직렬화).

8. 기록: audit와 state (2분)

보여줄 페이지: audit.md, aidlc-state.md

  • audit.md에는 사용자 입력 원문, 승인 시각, AI 응답이 순서대로 남는다. 누가 언제 무엇을 결정했는지 추적할 수 있다.
  • aidlc-state.md는 스테이지별 진행·승인 상태를 보여 준다.

9. 정리와 Q&A (8분)

보여줄 페이지: 사례 개요 — 건너뛴 단계

  • 영상의 정리 두 줄:
    • 질문과 승인으로 빈틈을 개발 전에 메웠다.
    • MVP까지는 빠르다. 상품 수준은 AI가 추정해 채운 부분을 사람이 계속 메워야 한다.
  • 함께 이야기할 거리: 이번에 건너뛴 단계가 필요한 프로젝트는 무엇인가, 범위가 바뀌었을 때 앞 단계 설계 문서는 누가 맞출 것인가.
